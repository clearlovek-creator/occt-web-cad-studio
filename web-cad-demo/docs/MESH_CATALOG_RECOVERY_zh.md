# 网格历史后台恢复

网格任务历史现在通过现有材料线程池恢复，不再在 Gateway 构造时同步扫描、读取和解析全部任务。恢复期间几何与其他服务可以继续工作；网格列表、创建、结果读取及文件下载归属判断必须等待完整目录，不能把尚未恢复的空 Map 当作“没有历史”。本批是独立候选，没有更新日常服务。

## 状态与错误处理

健康接口新增 `meshCatalog`，提供 `recovering`、`ready`、`unavailable` 或停止状态。只有 `ready` 才报告已知任务数；此前 `meshTaskCapacity.stored` 为 `null`，不是零。目录的成功或失败终态必须等材料线程实际退出，超时和停止不把迟到结果发布为有效目录；状态查询可以立即返回当前阶段。

目录恢复失败时，网格接口返回 503 及具体的 `MESH_CATALOG_*` 错误，不返回成功的空列表，不准入新任务，也不把未知下载文件当作独立文件工具的产物。它不会阻止其他工程的 OCCT 建模。恢复失败不自动反复重扫；按错误核对原始数据后，可在网格工具中手动重新读取，无需为此重启整个服务。不要删除工程或网格文件来“重置”状态。

| 错误 | 含义与处置 |
| --- | --- |
| `MESH_CATALOG_LIMIT` | 条目、任务、字节或时间预算不足。保留原目录，检查是否包含异常大记录或超出支持容量的历史；不得把部分结果当作完整清单。 |
| `MESH_CATALOG_ID_CONFLICT` | 不同工程目录中出现相同任务 ID。保留两份原记录，核对来源；系统不会挑选一份覆盖另一份。 |
| `MESH_CATALOG_UNSAFE` | 目录存在链接、联接或观察到的身份替换。恢复安全目录关系后重试，不跟随链接读取或清理。 |
| `MESH_CATALOG_UNAVAILABLE` | 恢复线程、读取或发布暂时不可用。原材料保留，通过诊断检查原因；不假装结果损坏或历史为空。 |

单份损坏、无效 UTF-8、缺失或非独立普通记录仍在其真实工程中显示失败条目，原字节保留。暂时无法读取与损坏分开标记；这类未经验证的任务不会触发临时来源清理。普通恢复结果保持隐藏，保存过的质量概要不能代替网格材料的重新验收。

## 在网格工具中重新读取

网格工具将“历史未就绪”原因放在操作区上方，沿用当前浅色工业主题、语义颜色与 40px 操作控件，没有新增弹窗或保存新的界面规范。恢复中或读取失败时不显示零条记录，也不显示“当前工程还没有剖分任务”；剖分与诊断按钮等待完整目录，当前参数仍保留。

先核对并修正提示所指的数据或访问条件，再按“重新读取网格历史”。此操作针对整个网格历史目录，成功后只在当前页面列出当前工程的记录。它不修正冲突文件内容、不选择其中一份来源、不扩大恢复预算，也不会重做剖分或修改几何。临时来源清理失败数量进入恢复统计，但不将有效网格判为损坏。

如果请求回复丢失，页面只查询后台状态，不再次发送重读命令；无法核对时改为“核对读取状态”。关闭工具不重放命令，切换工程后的旧回复不能覆盖新页面。通过键盘发起的重读成功后，记录区展开并获得焦点；若焦点已经移到其他可聚焦控件，则不抢回。成功信息明确说明没有重新剖分。

后台目录已就绪与当前工程列表已核对分别记账。即使后台重读成功，只要随后列表读取断网，页面仍显示“未读取”或最后已观察到的读取阶段，不显示成功、空列表或开放旧记录操作。只读核对拿到有效列表后，状态与行一起发布，并清除目录观察的旧网络错误；未确认创建或取消的警告不因此被清除。

## 恢复接口与准确操作身份

`GET /api/mesh/catalog` 返回当前目录状态，不触发扫描。状态格式版本为 1，包含每次实际恢复的 `attemptId`、是否允许重读、已知或未知的任务数量，以及失败代码。服务重启或开始新的恢复会生成不同身份。

`POST /api/mesh/catalog/recover` 只接受 `{"failedAttemptId":"准确的失败身份"}`，不能传入新预算。只有当前失败目录允许开始恢复。重复发送同一已接受请求，在同次恢复进行中返回 202，成功后返回当前状态；如果新恢复也失败，迟到的旧请求返回 409，不会再启动一次。已经就绪的目录不能通过该入口重扫或中断现有任务。

任务列表在启动恢复期间可以返回 503 `MESH_CATALOG_RECOVERING` 及准确状态，客户端需只读观察到目录就绪再取列表；CAD 已就绪不等于网格历史也已就绪。工作台已处理这一阶段，旧协议客户端应明确区分这两种就绪状态。单次读取仍使用原线程、并发与超时边界，不新增自动重试队列。

## 扫描与发布边界

扫描使用目录流，不先把整个目录列表读入内存。目录、任务 ID 和元数据身份逐项核对；跨工程重复任务 ID 会使全目录拒绝。相应目录的身份在结束时再次核对，父目录链接也拒绝。它不是操作系统目录锁或任意恶意竞态的认证。

默认上限为 50000 个目录条目、10000 个任务、64 MiB 元数据总量、16 MiB 单记录与 30 秒扫描。未知条目和已删除任务仍消耗清点预算，不通过忽略它们绕过限额。调用方只能降低研究或测试额度，不能通过请求放大默认上限。

字节预算按同一实际打开文件描述符核对的长度计费，并在缓冲分配和 JSON 解析之前检查。文件在早期检查后增大不能少记账，格式损坏的输入也消耗已读取字节预算。文件身份、长度与时间在读取前后核对，JSON 按严格 UTF-8 解码。

全量扫描通过后才逐条将未完成任务记为 `interrupted`，不会重放旧剖分。扫描预算或身份检查失败前不写中断状态；扫描成功后的多条状态保存不是跨记录联合事务，中途 I/O 故障可能已保存部分中断状态，但不会发布部分目录。临时来源的清理改为异步执行，失败不把有效原网格标为损坏。

在线恢复复用现有重计算名额、材料线程、180 秒包含排队的处理截止和 64 MiB 回复额度，不增加平行服务或恢复队列。线程既有老代 1 GiB 限额、逻辑元数据额度和任务数上限不是 Gateway 全进程 RSS 硬限制；较大的结构克隆及主线程接收仍有开销。

## 验证范围

新增 16 项恢复测试，覆盖完整计数、旧活动任务中断、预算拒绝前不改原状态、跨工程身份冲突、损坏材料、硬链接和目录替换、实际打开字节计费、真实线程隔离、发布前退出及关闭时迟到回复。原有显隐与生命周期夹具改为等待明确的恢复就绪，再注入受控测试记录，没有取消旧断言。

`scripts/verify-mesh-catalog.mjs` 在准确封存候选上运行真实 HTTP、OCCT 与 Gmsh：冲突目录不能列空历史或开始新剖分，但建模仍可用；正常共形网格在服务重启后恢复、保持隐藏，显示前重新验收，Body 与六个 Face 的来源保持。该脚本使用独立目录与端口，没有付费模型调用。

`scripts/benchmark-mesh-catalog.mjs` 生成 4 个工程、2000 条合法历史记录，每条来源包含 60 个 Body，共约 19.9 MB 元数据。参考与线程模式在独立 Node 进程中顺序运行，核对完整结果摘要相同及元数据未变；记录恢复耗时、主线程计时间隔和进程 maxRSS。它是合成元数据压力，不是实际工业 CAD、网格剖分或显卡基准，也不测量完整服务启动和临时来源清理。

最终分层数量、候选身份、较空闲测量及保护核对以 `.artifacts/mesh-catalog-result.json` 关联的原始证据为准。早期因夹具在恢复前直接注入 Map 而等待的日志、首批候选和并行负载测量保留，不混作最终源码验收。

后续交互批次新增 7 项后台与 12 项客户端测试。`scripts/verify-mesh-catalog-ui.mjs` 在实际失败目录上验证重复失败、保留两份原记录、修正目录后重读、受控丢回复仅查询状态、后台就绪但列表断网、参数保持和键盘焦点；1440、900、640 宽度截图核对了文字对比、换行及按钮范围。最终交互版本与分层结果见 `.artifacts/mesh-catalog-ui-result.json`，不能将前一批页面视为已含新交互。

交互批次最终完整 2012 项应用及 94 项 Python 回归、6 项专门页面流程和 76 项工作台兼容流程通过。三份旧恢复夹具改为等待准确的目录就绪状态，原质量、来源与重开断言保留，没有重发建模命令。列表断网反例先复现了错误的成功提示，再验证修复；后台真实完成与页面观察到完成分开检查，不用固定等待猜阶段。历史引用页面首轮曾等待输入预览超时；增加实际失败响应记录后，两轮 8 条流程通过，但根因尚未确认，不据此宣称该间歇异常已修复。首轮日志、截图及后续诊断均保留。

## 后续范围

历史引用间歇异常的后续检查确认原页面包含任务阶段保存失败。独立批次修复了记录已发布却被后续清理误报失败的路径，并增加真实文件占用诊断与旧版页面对照；原当时的具体系统错误仍未取得。详见 [任务记录保存与诊断](TASK_RECORD_PERSISTENCE_zh.md)，不将网格历史恢复功能与该问题混为同一原因。

当前已支持后台完整恢复、失败后的手动重读及丢回复状态核对，尚未提供冲突文件内容或归属的自动修复、无限历史分页、任意规模目录支持或低开销分批结构传输。完整安装升级、跨数据版本迁移、复杂拓扑属性、工业脏几何与真实大工程性能仍属于整体前处理工业化目标。

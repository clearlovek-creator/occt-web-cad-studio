# 独立工作台组合候选

组合封存前端 V2、后台 V3、OCCT/Gmsh 运行库、Pi SDK 与 Node。Node 24.22.3 配套候选已完成本机隔离验证，准确版本与结果见 `.artifacts/projection-cancel-result.json`；早期组合凭据保留在 `.artifacts/workbench-bundle-result.json`。这是便携候选，不是已发布安装器，日常服务不更新。

早期组合的 9 项整包验收、1854 项应用回归、94 项内嵌 Python 回归、19 项既有内核测试及 27 项受管服务流程通过。它们不能作为后续新运行时或新原生组件的整包验收结果；下述全新系统、安装/升级与许可边界保持未完成。

## 目录与版本边界

```text
workbench-时间-UUID/
  Start-WebCAD.ps1          启动、状态、停止入口
  workbench.json            固定整套版本、文件清单与外部边界
  app/                     受管服务控制器及封存项目模块
  node/                    Node、完整许可来源与校验凭据
  frontend/frontend-.../    自包含页面版本
  backend/backend-.../      后台、原生运行库及原生 Pi SDK
```

早期组合约 500 MiB，7444 份随包材料，不复制工作区源码目录、开发依赖、用户 `.env`、工程、供应商密钥或 Pi 历史。源码模块的封存副本当然属于运行代码，不等同于需要开发工作区。已有源快照、原生 DLL 分组及 SDK 清单保持原校验，不把上层组合清单替代子组件验证。

包含新原生组件和 Node 24.22.3 的材料已超过旧整包 512 MiB 上限。整包改为独立的 1 GiB、10000 文件总预算，最终 `workbench.json` 也计入，发布前检查完整材料；前端、后台、控制代码和 Node 各自仍使用原有 512 MiB、10000 文件清点及更细的专属校验。仅允许固定组件目录、启动文件和组合清单，不能用额外根目录或排除清单绕过总预算。原始超限暂存保留；新候选含最终清单共 7565 文件、541859294 字节，实际启动验收通过。

构建要求明确指定前后端根目录、Node 来源材料和输出目录，没有日常服务默认目录或自动部署。先选择经过验收的 Node 程序；前端、后台、Pi SDK 和组合包必须使用同一精确版本构建，不能只更换已经封存版本中的 `node.exe`：

```powershell
$node = '<已验证的 Node 程序绝对路径>'
& $node scripts/acquire-node-runtime.mjs --output .artifacts/node-source-input
& $node scripts/build-workbench-bundle.mjs --frontend-root <同版本前端候选根目录> --backend-root <同版本后台候选根目录> --node-material .artifacts/node-source-input --output-root .artifacts/workbench-candidates
```

`acquire-node-runtime.mjs` 只下载当前调用程序对应版本的公开校验文本及完整 LICENSE，不下载或执行新程序。早期组合使用本机 Node 24.14.0，其 Windows x64 程序 SHA256 为 `63c259c81e5d472b5f11c8d506070130cb04a1ecf84b80377a34ed6ec9048088`，与 [Node 官方发布清单](https://nodejs.org/dist/v24.14.0/SHASUMS256.txt) 对照一致。来源校验只能证明字节身份，不能证明没有运行时缺陷；该版本后续已在真实线程取消中复现访问异常，不作为新的稳定性验收基线。来源材料通过 HTTPS 获取，不是 PGP 签名验证或整包签名认证。

Node 为独立 PE32+ AMD64 程序，当前静态/延迟导入均属于明确的 Windows 系统依赖；发现非系统 DLL 则拒绝，不从开发 PATH 猜测。Node 单映像上限 128 MiB 只通过显式参数用于它自己的检查，既有原生内核的 64 MiB 单映像限制未放宽。程序哈希和 PE 解析使用同一份字节，再写出这一份字节。

## 线程退出稳定性

Node 24.14.0 在网格材料线程真实取消和超时退出时出现 `0xC0000005`。同版本官方符号将故障定位到 `ContextifyScript` 的 cppgc 最终回收函数，在 Worker 隔离环境析构时写入已经释放的 Realm。[Node 24.22.0](https://nodejs.org/en/blog/release/v24.22.0) 包含释放 Realm 前分离 cppgc 包装对象的修复。不能通过取消强制退出、跳过忙碌线程测试或放宽暂存清理屏障绕过它。

独立 Node 24.22.3 已核对[官方程序校验值](https://nodejs.org/dist/v24.22.3/SHASUMS256.txt)、完整许可和 PE 依赖，程序 SHA256 为 `86fc4785327db5f5c7558dc6156c543b433c313e813a222e088086222ab4afa6`。20 轮、每轮 25 项网格来源适配及真实取消检查，以及两轮每轮 2540 项完整应用回归通过。容量修正后的最终 2547 项回归通过，875 份项目文件前后摘要一致；另有 50 项相关边界、21 项原生、7 项配套页面、7 项构建输入保护及 9 项实际整包流程通过。

整包在带中文和空格的空白宿主中，使用系统 PATH 和故意失效的开发环境覆盖，验证随包 Node、真实浏览器/Pi/MCP/OCCT 建模、Gmsh、工程保存打开、原生消息恢复、损坏拦截与正常停机。原生程序与同一测试清单绑定，所有管理进程已退出。中间因源码更新被完整性门禁拒绝的回归记录保留，不能与冻结源码的最终通过记录混用。完整结果见 `.artifacts/projection-cancel-result.json`，这仍不是全新操作系统、安装升级、完整许可或工业规模验收。

后续使用新运行时需保留旧失败日志、精确符号与原生来源证明，重新构建配套版本并完成整包验收。系统 Node 和日常服务不随此验证自动替换。此问题与 Netgen 原生优化进程的偶发访问异常分别追踪，不能用 Node 验收代替 Netgen 修复。

## 启动与数据

在版本内运行 `Start-WebCAD.ps1`，使用 `-Action Start/Status/Stop`，可以明确传入 `-DataDirectory`、`-RuntimeDirectory`、前后台端口及 `-AsJson`。不自动启动浏览器或刷新正在使用的页面。

工程与服务记录必须位于版本目录外；已有目录链中的链接/联接点也会拒绝，防止字面上的外部路径实际回到只读发布目录。默认用户数据在 `%LOCALAPPDATA%\WebCAD\Workspace`，服务记录在其同级 `Workspace-runtime`；本批验收始终显式选择专属临时目录和独立端口，没有采用这些日常默认入口。

启动先验证控制代码与 Node，再由随包 Node 检查整包及子组件。清理继承的 Node 注入配置和开发运行路径，强制服务使用已验证的随包程序；项目资源放入数据目录的 `agent-skills` / `agent-knowledge`，Pi 工作目录及配置也在用户数据中。不会启动 npm 安装、查找宿主开发依赖或回退源码。

精简环境验收发现 Windows PowerShell 在缺失 `PATHEXT` 时会把 `.exe` 当成文档，出现空退出码或 `CantActivateDocumentInPipeline`，并非模型或前端文件损坏。启动入口与控制器为当前进程设置明确的 Windows 可执行扩展名，不修改用户/系统级环境。控制器的一次性 Node 命令还改为直接启动真实进程、准确转义参数、独立读取 UTF-8 输出和核对退出码；中文路径、引号、尾随反斜线和空参数均有实际进程测试。停止路径也保留此环境默认值，不能只在启动时修复。

`Status/Stop` 仍要求控制脚本完整，但不依赖 Node/原生文件完整，便于在运行材料损坏后安全停止既有注册进程。受管控制器继续验证 PID、启动身份、可执行文件和准确脚本路径，不按端口杀进程；后台优先正常排空与退出。更换 Node 路径不能悄悄复用或重启旧进程。

## 首次检查的真实时限

首轮逐文件记录证明，并非某个文件永久卡住：数千份 SDK/原生文件的首次完整清点持续前进，整套检查约 73 秒才读到第二轮 SDK 尾部；随后同一路径的独立读取约 4 秒。二者是当前机器/缓存条件下的观察，不是通用启动性能保证，也未据此确认防病毒或磁盘是唯一原因。

原 60 秒观察上限不足，导致校验进程尚未退出就被报告未确认。现使用实际进程身份及退出码，默认 `-VerificationTimeoutSeconds 180`（允许 30–600 秒），有界输出“清单、文件、Node、前端、后台”阶段。时限到达不会自动杀进程、启动服务或改用其他版本；应保留材料并检查原 PID。验收工具的观察预算与此区分，不把等到超时当成退出证据。

首轮临时诊断候选在专属系统临时目录记录了 I/O 路径/操作，而不是文件内容或密钥，未改变哈希与验收条件。记录保留 `.artifacts/workbench-bundle-cold-io.jsonl`，相关冻结候选也保留；最终运行入口已移除该临时文件跟踪，只输出有界阶段信息。早期空退出码和超时凭据不覆盖。

## 验收和未完成项

`scripts/verify-workbench-bundle.mjs --bundle <准确版本目录>` 复制到带中文和空格的空宿主，使用系统 PATH 与故意失效的开发环境覆盖，验证实际服务程序归属、原生助手工具/CAD/视口更新、Gmsh、工程保存打开、完整消息恢复、损坏拒绝及安全停止。模型为本地协议夹具，既不收费，也不代表供应商在线可用性或模型智能验证。

最后一项会真实破坏私有副本的 Node 字节，确认其在执行应用代码之前被拒绝，停止的注册记录和工程退出凭据不变。该损坏副本及测试材料明确保留供核对，不把刚使用的 EXE 原地截断覆盖当作升级策略。早期夹具在原地恢复时遭遇 Windows `EBUSY`，未确认具体持锁者，不能据此宣称有孤儿进程或归因于防病毒；最终另核对没有存活测试进程。原封存版本始终保持完整。

后续构建候选增加[路径与输入准入](BUNDLE_BUILD_ADMISSION_zh.md)：输出不得嵌入输入、工作区受保护目录或既有版本，坏材料不能提前创建目录；规范路径、联接和目录身份变化都有检查。准确新候选以该专项回执为准，不能将早期便携版本改写为已具有新防护。此层仍不是操作系统目录锁或任意恶意文件系统竞态的认证。

仍需全新 Windows/虚拟机上的系统先决条件验收、系统浏览器兼容、完整第三方许可与交付条件审计、完整安装/更新入口、跨数据版本升级回滚、签名及成套用户历史迁移。当前清单明确标记 `thirdPartyLicenseAudit: incomplete`，不得将便携候选或绿色局部测试当作完整可对外发布产品。I4 复杂拓扑属性、I5 工业脏几何与离散交叉、I6 大工程/显卡规模及整体工业化目标继续保留。
